# Запуск и эксплуатация

## Требования к окружению

Docker Engine или Docker Desktop с Linux-контейнерами, Docker Compose v2, Bash, Python 3 и curl. NET_ADMIN должен быть доступен firewall-контейнерам. Используемые подсети не должны пересекаться с существующими сетями Docker или маршрутами окружения.

```bash
docker version
docker compose version
python3 --version
curl --version
df -h .
```

## Первое включение

Все команды выполняются из корня проекта.

```bash
bash scripts/start.sh
```

Скрипт создаёт `.env` со случайными паролями, необходимые локальные каталоги и файл `runtime/db-host`. Затем проверяет конфигурацию, собирает образы и запускает сервисы с ожиданием готовности.

Интерфейс доступен на http://localhost:8080. Если Docker работает внутри виртуальной машины, первоначальную проверку выполняют из этой виртуальной машины.

Файл `.env` нужно сохранять при использовании существующих томов. Повторная генерация паролей без изменения учётных данных в сохранённой БД может нарушить подключение приложений.

Compose использует имя проекта `rk1-desk`. Несколько рабочих копий с этим именем обращаются к одному набору ресурсов Docker. Для отдельного окружения требуется согласованное изменение имени проекта, сетей и опубликованного порта.

## Состояние и журналы

```bash
docker compose ps --all
docker compose logs --tail=80 db db-standby api worker
docker compose logs --tail=50 nats1 nats2 nats3 firewall-api firewall-worker
curl -fsS http://localhost:8080/api/diagnostics
```

`/api/live` проверяет HTTP-процесс. Подробная диагностика зависимостей находится в `/api/diagnostics`.

## Сборка образов

```bash
docker compose build
```

Команда пересобирает образы и сама по себе не переключает роли БД. Обычный запуск через `scripts/start.sh` допустим, пока `runtime/db-host` указывает на `db`.

## Работа после переключения БД

После успешного `scripts/db-failover.sh` основным становится `db-standby`. Старый `db` должен оставаться остановленным. Обычный `docker compose up` может запустить прежний узел; его нельзя использовать для возобновления этой топологии.

```bash
bash scripts/resume-after-failover.sh
```

Скрипт оставляет прежний primary остановленным, запускает инфраструктуру и возобновляет прикладные контейнеры. После проверки подключений данные продолжают записываться в повышенный standby.

## Резервное копирование

```bash
bash scripts/backup-restore.sh
```

Создаётся дамп текущей основной БД в формате `pg_dump -Fc`, затем выполняется восстановление в отдельную проверочную БД. Файл остаётся в `backups/`. Исходная БД не перезаписывается.

Копии на том же хосте не защищают от потери хоста. Для эксплуатации нужны независимое место хранения, политика сроков хранения и регулярные проверки восстановления. Автоматическое расписание копирования в проекте не настроено.

## Сброс окружения

```bash
bash scripts/reset-demo.sh --discard-demo-data
```

Команда сохраняет текущую БД в `backups/`, удаляет контейнерные тома этого Compose-проекта и развёртывает исходную пустую топологию. Заявки и сообщения в работающем окружении будут удалены. Файл резервной копии на хосте сохраняется.

Если создание копии завершается ошибкой, скрипт прекращает работу до удаления томов. Этот сценарий предназначен для полного сброса данных; он не реализует возвращение старого primary как реплики с сохранением текущего кластера.

## Секреты и локальные данные

В Git исключены `.env`, содержимое `runtime/`, `backups/`, `evidence/` и журналы. Пустые `.keep` сохраняют структуру каталогов. Пароли и дампы нельзя публиковать через ручную загрузку файлов.

Для публичного размещения необходимо отдельно настроить аутентификацию пользователей, TLS, сетевую политику и управление секретами.
