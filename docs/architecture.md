# Архитектура приложения

Приложение состоит из веб-интерфейса, HTTP API и фонового обработчика. Компоненты работают отдельными процессами в контейнерах. API и worker используют общую PostgreSQL; такое размещение данных связывает их с общей схемой БД.

## HTTP API

| Метод | Путь | Действие |
|---|---|---|
| GET | `/api/hello` | Сообщение микросервиса |
| GET | `/api/live` | Проверка работы HTTP-процесса |
| GET | `/api/tickets` | Список заявок |
| POST | `/api/tickets` | Создание заявки |
| PUT | `/api/tickets/{id}` | Изменение темы и статуса |
| DELETE | `/api/tickets/{id}` | Удаление заявки |
| GET | `/api/notifications` | Последние уведомления |
| GET | `/api/diagnostics` | Состояние БД, Redis и потока JetStream |

Название заявки должно содержать текст и иметь длину не более 200 символов. Статус принимает значения `open` и `closed`. Пользовательские значения передаются в SQL параметрами psycopg.

## Данные

Схема находится в `db/schema.sql`.

| Таблица | Назначение |
|---|---|
| tickets | Заявки, статусы и время создания |
| outbox | События и время подтверждения публикации |
| processed_events | Идентификаторы обработанных событий |
| notifications | Уведомления по событиям создания заявок |

Идентификатор события уникален в `processed_events` и `notifications`. Уведомления сохраняют историю создания заявок и не удаляются при удалении самой заявки.

## Публикация и потребление

1. API сохраняет новую заявку и событие в одной транзакции.
2. Издатель выбирает записи outbox без `published_at`.
3. Событие публикуется в subject `tickets.created` потока `TICKETS`.
4. После подтверждения JetStream издатель заполняет `published_at`.
5. Worker получает событие через durable-потребителя `notifications-worker`.
6. Worker одной транзакцией сохраняет `event_id` и уведомление.
7. После фиксации транзакции отправляется ACK.

Сбой между публикацией и отметкой в outbox может привести к повторной отправке. Повторная доставка после записи уведомления, но до ACK также возможна. Идемпотентность записи предотвращает повторное уведомление. Общая гарантия exactly-once для всей системы не заявляется.

Поток использует файловое хранение, три реплики и срок хранения сообщений 24 часа. Доставка отложенного сообщения зависит от того, что оно ещё находится в потоке.

## Кэширование

API читает версию ключа `tickets:version` и ищет список по ключу `tickets:list:<version>`. При отсутствии списка выполняется SQL-запрос и результат сохраняется в Redis на 30 секунд. Создание, изменение и удаление заявки увеличивают версию ключа.

| X-Cache | Источник ответа |
|---|---|
| HIT | Redis |
| MISS | PostgreSQL с последующим заполнением Redis |
| BYPASS | PostgreSQL при недоступности кэша |

Если Redis был недоступен в момент изменения данных, восстановившийся кэш может содержать старый список до истечения TTL. Строгая согласованность кэша не обеспечивается.

## Сетевые сегменты

| Сеть | Подсеть | Участники |
|---|---|---|
| edge | 172.30.10.0/24 | frontend, API |
| data | 172.30.20.0/24 | API, worker, primary, standby |
| cache | 172.30.30.0/24 | API, Redis |
| messaging | 172.30.40.0/24 | API, worker, nats1–nats3 |

Сети data, cache и messaging имеют `internal: true`. Frontend подключён только к edge. На хост опубликован только `127.0.0.1:8080`.

## Правила доступа

Firewall-контейнеры разделяют сетевое пространство с API и worker и получают NET_ADMIN. Их правила не изменяют firewall хоста.

| Источник | Назначение | Порт |
|---|---|---|
| frontend | API | TCP 8000 |
| API | primary и standby | TCP 5432 |
| worker | primary и standby | TCP 5432 |
| API | Redis | TCP 6379 |
| API и worker | nats1–nats3 | TCP 4222 |

В пространствах API и worker политики INPUT и OUTPUT установлены в DROP. Дополнительно разрешены loopback, DNS и ответы на установленные соединения. Обращение API к мониторингу NATS на 8222 запрещено. PostgreSQL ограничивает источники подключений через `pg_hba.conf`.

## Восстановление после отказа

JetStream выбирает нового лидера потока при сохранении кворума. Три реплики позволяют выдержать отказ одного узла брокера.

PostgreSQL использует асинхронную потоковую репликацию. Повышение standby и смену адреса для приложений выполняет `scripts/db-failover.sh`. Текущий адрес находится в `runtime/db-host` и читается при создании SQL-подключений.

После переключения прежний primary остаётся остановленным. Для восстановления резервирования требуется корректное возвращение узла в кластер или переинициализация окружения. Размещение всех контейнеров на одном хосте не защищает от потери этого хоста.
