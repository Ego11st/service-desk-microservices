# Проверка приложения

В документе приведены команды и критерии успешного выполнения проверок. Результаты относятся к конкретному прогону и должны фиксироваться по его фактическому выводу.

## Исходное состояние

```bash
bash scripts/start.sh
docker compose ps --all
curl -fsS http://localhost:8080/api/hello
```

Сервисы должны работать; компоненты с healthcheck должны перейти в состояние healthy. `/api/hello` возвращает JSON с сообщением микросервиса.

## Функциональная проверка

```bash
python3 scripts/smoke.py
```

Проверяются создание, чтение, изменение и удаление заявки; заполнение и чтение Redis; инвалидация кэша; публикация и потребление события с созданием уведомления. При успехе вывод заканчивается строкой `PASS: CRUD, cache, invalidation and broker delivery`.

Тест удаляет созданную им заявку. Уведомление об её создании сохраняется в истории. Для получения результатов в файлах:

```bash
bash scripts/evidence.sh
```

Команда сохраняет сведения о контейнерах, правилах, реплике, состоянии зависимостей и функциональном прогоне в `evidence/`.

## Сетевые ограничения

Выполняются до переключения БД.

```bash
bash scripts/firewall-demo.sh
docker compose exec -T firewall-worker iptables -S
```

Критерии: API подключается к PostgreSQL:5432; обращение к мониторингу NATS:8222 блокируется; после временного запрета легитимного SQL-соединения HTTP-запись получает 503; после снятия правила запись проходит.

Скрипт устанавливает временный DROP перед правилом established. EXIT-trap снимает его при завершении. При принудительном прерывании нужно проверить правила и при необходимости перезапустить firewall-api.

## Отказ брокера

```bash
bash scripts/broker-failover.sh
```

Скрипт определяет действующего лидера потока, завершает его SIGKILL, ожидает выборов и запускает функциональную проверку с двумя оставшимися узлами. После проверки остановленный узел запускается обратно.

Критерии: лидер меняется, публикация и обработка события продолжаются. Наличие трёх контейнеров без трёх реплик потока не подтверждает такую устойчивость.

## Отказ PostgreSQL

Выполняется после проверок обычной топологии.

```bash
bash scripts/db-failover.sh
```

Сначала проверяются режим recovery и воспроизведение конкретной позиции WAL на standby. Затем primary аварийно завершается, standby повышается через `pg_ctl promote`, файл маршрута переключается и запускается функциональная проверка.

Критерии: прежний primary остановлен; `pg_is_in_recovery()` на новом primary возвращает false; CRUD и обработка событий работают после смены адреса.

Переключение выполняется скриптом вручную. Асинхронная репликация не даёт общей гарантии RPO=0. Для повторения проверки нужно восстановить исходную топологию; порядок возобновления и сброса описан в [эксплуатации](operations.md).

## Восстановление копии

```bash
bash scripts/backup-restore.sh
```

Критерии: создан непустой дамп, pg_restore завершился без ошибок, восстановленная БД содержит ожидаемые данные. При сравнении количества записей не должно быть параллельных изменений и ожидающих обработки событий.

## Оценка восстановления

RTO задаёт допустимое время восстановления, RPO — допустимую потерю последних данных. Фактическое время фиксируют от момента отказа до успешной пользовательской операции. Один эксперимент даёт длительность одного восстановления; для MTTR и MTBF нужна статистика нескольких событий и эксплуатационных интервалов.

Пример целевого SLO — 99% успешных пользовательских запросов за 30 дней. Это требование к будущим измерениям, а не результат функционального прогона. Все контейнеры размещены на одном хосте; отказ целого хоста не покрывается этими проверками.
